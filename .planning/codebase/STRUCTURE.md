## Directory Purposes

**`src/` — Backend API:**
- Purpose: All server-side logic for routing, DB operations, AI integrations
- Contains: TypeScript source files
- Key files: `index.tsx` (280K+, main), `routes/*.ts` (modular endpoints), `helpers.ts` (reusables)
- Build process: Vite + @hono/vite-build compiles to `dist/_worker.js` for Cloudflare Pages Functions

**`public/static/` — Main App Frontend:**
- Purpose: Single-page app for students and mentors
- Contains: Minified JavaScript (app.js 800K+), compiled CSS, PWA assets, images
- Key files: `app.js` (all screens), `app.css` (layout + responsive), `sw.js` (service worker)
- Load method: Embedded in HTML template returned by backend

**`public/modules/records/` — Records Module (Isolated SPA):**
- Purpose: Pluggable micro-app for recording class, exams, activities, assignments
- Contains: Self-contained router, state, views, API client
- Key files:
  - `records.js` — exports `init()`, `navigate()`, `getState()` for embedding
  - `core/state.js` — centralized state with 80+ properties
  - `core/api.js` — all DB API calls (prefixed with `/api/student/:id/`)
  - `views/*.js` — 38+ screen renderers (template literals + handlers)
- Features: Standalone test via `dev.html` (no login), or embedded in main app
- Namespace isolation: `_RM` prefix for globals to avoid collision with main app

**`schema/` — Database Schema:**
- Purpose: D1 database structure (SQLite)
- Contains: 14+ tables covering users, groups, records (class/exam/activity/assignment), community, feedback
- Key tables: `students`, `class_records`, `exam_results`, `question_records`, `activity_records`
- Access pattern: Only backend can modify; queries constructed in `src/routes/*.ts`

**`dist/` — Build Artifacts:**
- Purpose: Output from Vite build (generated, not committed in typical setup)
- Contains: `_worker.js` (Cloudflare Functions), compiled static files
- Generated by: `npm run build` → Vite processes `src/index.tsx` + `public/` → outputs to `dist/`

**`migrations/` — Database Migrations:**
- Purpose: Track schema changes as SQL files
- Contains: ALTER TABLE statements for adding columns/tables
- Example: `add_parent_id_to_class_records.sql`, `create_xp_history_table.sql`

## Key File Locations

**Entry Points:**

- **Backend:** `src/index.tsx` — Hono app initialization, route mounting, middleware setup
- **Frontend (Main):** `public/static/app.js` — Loaded in `index.html` by backend renderer
- **Frontend (Records Module):** `public/modules/records/records.js` — Imported by main app or standalone test
- **Database:** `schema/full_database_schema.sql` — Defines all tables; applied via `/api/migrate` endpoint

**Configuration:**

- `tsconfig.json` — TypeScript strict mode, JSX (Hono), module resolution
- `vite.config.ts` — Defines Vite + Hono build plugins, entry point `src/index.tsx`
- `wrangler.jsonc` — Cloudflare Pages config: D1 database name, R2 bucket name, compatibility date
- `.dev.vars` — Local env vars for development (API keys, not committed)

**Core Logic:**

- Backend routes: `src/routes/mentor-*.ts` (all endpoints grouped by domain)
- Backend helpers: `src/helpers.ts` (400+ lines: Gemini, Claude, crypto, validation)
- Frontend state: `public/modules/records/core/state.js` (80+ properties, Proxy-based reactivity)
- Frontend router: `public/modules/records/core/router.js` (screen navigation, history)
- Frontend API: `public/modules/records/core/api.js` (20+ methods for CRUD operations)

**Testing:**

- `public/modules/records/dev.html` — Standalone records module test (includes mock data loader)
- No unit tests in this codebase (no test framework configured)

## Naming Conventions

**Files:**

- **Route modules:** `kebab-case` + domain prefix: `mentor-auth.ts`, `mentor-student.ts`
- **Views (frontend):** `kebab-case` + feature prefix: `class-record.js`, `exam-add.js`, `photo-upload-v2.js` (v2 indicates iteration)
- **Core modules:** Simple names: `state.js`, `router.js`, `api.js`, `events.js`, `utils.js`
- **Styles:** `kebab-case.css`: `app.css`, `records.css`, `app-mentor.js` (for mentor dashboard)

**Functions & Variables:**

- **Backend:** `camelCase` for functions (`verifyPassword`, `getStudentCareerContext`), `UPPER_SNAKE_CASE` for constants (`SYSTEM_PROMPT_CREDIT_LOG`, `GEMINI_MODEL`)
- **Frontend (Main App):** Global functions prefixed with underscore to avoid collisions: `_loadStudentData()`, `_showExamForm()`, `_saveClassRecord()`
- **Frontend (Records Module):** Namespaced under `_RM` for globals, camelCase for internal functions. Event names: `EVENTS.RECORD_SAVED`, `EVENTS.STATE_CHANGED`

**Directories:**

- Domain-organized: `routes/` (backend), `modules/` (frontend features), `views/` (screens), `core/` (infrastructure)
- Lowercase with hyphens: `public/modules/records/views/`, `public/modules/records/core/`

## Where to Add New Code

**New API Endpoint:**

1. Determine domain: student data → `mentor-student.ts`, community → `mentor-community.ts`
2. Add to corresponding file in `src/routes/`, following pattern:
   ```typescript
   routerInstance.post('/api/student/:id/new-feature', async (c) => {
     // validate input
     // query DB via c.env.DB
     // return c.json({ success: true, data: {...} })
   })
   ```
3. Frontend calls via `fetch(`/api/student/${studentId}/new-feature`, { method: 'POST', ... })`

**New Screen/View (Records Module):**

1. Create file: `public/modules/records/views/feature-name.js`
2. Export two functions:
   ```javascript
   export function registerHandlers() {
     // attach event listeners to DOM
   }
   export function renderFeatureName() {
     return `<div class="...">...</div>`
   }
   ```
3. Register in `public/modules/records/records.js`:
   - Import: `import { registerHandlers, renderFeatureName } from './views/feature-name.js'`
   - Add to SCREEN_MAP: `'feature-name': renderFeatureName`
   - Add to view registration: `registerView('feature-name', renderFeatureName, registerHandlers)`
4. Call from other views: `navigate('feature-name')`

**New Database Table:**

1. Add CREATE TABLE to `schema/full_database_schema.sql` (for reference)
2. Create migration file: `migrations/YYYYMMDD-create-new-table.sql` with ALTER or CREATE statement
3. Add `/api/migrate` endpoint handler to apply migration
4. Frontend: Add corresponding API method in `public/modules/records/core/api.js` with query pattern
5. Backend: Add query builder in corresponding `src/routes/*.ts` file

**New Utility Function:**

- Shared backend helpers → `src/helpers.ts`
- Shared frontend helpers → `public/modules/records/core/utils.js`
- Module-specific → declare at top of view file or in `core/`

## Special Directories

**`dist/` — Build Output:**
- Purpose: Compiled JavaScript, CSS, static assets for deployment
- Generated: Yes (by `npm run build`)
- Committed: No (added to .gitignore)
- Rebuild: Run `npm run build` after any source changes; commit only if deploying manually

**`.wrangler/` — Local Wrangler State:**
- Purpose: Cache, temporary bundles, local D1 database file
- Generated: Yes (by `wrangler` CLI)
- Committed: No
- When to clean: If local dev environment is corrupted, delete and re-run `npm run dev`

**`migrations/` — Schema Versioning:**
- Purpose: Track incremental DB changes (NOT auto-applied on deploy)
- Committed: Yes
- How it works: Each SQL file is a manual migration applied via `/api/migrate` endpoint
- Example: After adding `parent_id` column, developer runs `curl http://localhost:5173/api/migrate` to apply locally
- Important: Always backup D1 before applying migration to production

**`.planning/codebase/` — GSD Documentation:**
- Purpose: Architecture, testing, conventions analysis for code generation
- Generated: Yes (by `/gsd:map-codebase` command)
- Committed: Yes (helps team understand structure)
- Update when: Major architectural changes, new patterns emerge, tech stack changes
